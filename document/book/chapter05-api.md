# API

## API의 개요

### API의 개념
> `API`(Application Programming Interface)는 응용 프로그램에서 사용할 수 있도록 운영체제나 프로그래밍 언어가 제공하는 기능을 제어하기 위한 인터페이스이다.

### API 개발 순서
- 앤드포인트 설계
  - 요청을 보낼 서버의 주소를 설정하고, 해당 경로에 대해 어떤 API를 요청할지 최종 엔드포인트 정의한다.
- HTTP 메서드 지정
  - 각 엔드포인트에 요청할 HTTP 메서드를 지정한다.
- 데이터 포맷 및 프로토콜 선택
  - API에서 사용할 데이터 포맷, 즉 주고받을 데이터 형태와 통신에 사용할 프로토콜을 선택한다.
- 앤드포인트 구현
  - 각 엔트포인트로 접수된 클라이언트의 요청을 처리하는 서버 측 로직을 구현한다.
- 인증 및 보안
  - API를 보호하기 위해 인증 및 보안 매커니즘을 구현한다.
- 오류 및 예외 처리
  - 잘못된 요청이나 예외 상황에 대해 적절한 오류 응답을 할 수 있도록 프로그램 로직을 보강한다.
- 테스트와 디버깅
  - API 개발 작업은 테스트와 디버깅 단계를 거쳐야 한다.
- API 문서화
  - API를 사용하는 다른 개발자가 쉽게 이해하고 사용할 수 있도록 문서화하는 단계이다.

## API의 유형

### REST API

> API 작성 규칙을 표준화한 것이 `REST API`(REpresentational State Transfer API)이다.

#### 📍 REST API의 구성요소
- `자원`
  - REST API는 클라이언트와 서버가 주고받는 자원을 URI로 명시한다.
  - URI는 URL보다 상위 개념으로, 특정 자원 자체를 의미한다.
  - URL은 웹상에서 자원이 있는 곳의 위치를 뜻한다.
- `행위`
  - Create(데이터 생성): POST
  - Read(데이터 조회): GET
  - Update(데이터 수정): PUT or PATCH
  - Delete(데이터 삭제): DELETE
- `표현`
  - REST API는 변하는 자원 상태를 반영해 요청받은 시점의 자원 상태를 반환한다.
  - 이때, 주고받는 자원인 데이터의 형식은 JSON 또는 XML이다.

#### 📍 REST API의 특징

- HTTP 요청 메세지만 보고도 어떤 동작이나 정보를 요청하는지 쉽게 이해할 수 있어야 한다.

#### 📍 REST API 설계 규칙

- URI에 명사를 사용한다.
  - 잘못된 예) `GET / getUserById/: id` == `id번 사용자 id를 조회하는 것을 조회하라?`
  - 올바른 예) `GET / users/:id` == `id번 사용자를 조회하라`
- 자원의 계층 관계를 `/`로 나타낸다.
  - REST API는 `/` 구분자를 사용해 자원 간의 계층 관계를 나타낸다. 
  - 일반적으로 이러한 관계를 'has-a'  관계라고 한다.
- 마지막에 `/`를 넣지 않는다.
- 명사와 명사를 구분할 때 `-`을 사용한다.
- 소문자만 사용한다.
- 파일 확장자를 포함하지 않는다.
- 적절한 HTTP 상태코드를 응답한다.

### GraphQL

> `GraphQL`(Graph Query Language)은 클라이언트가 서버로부터 데이터를 효율적으로 가져오기 위해 개발되었다.

- `/graphql` 이라는 URI 하나로 필요한 데이터를 조합한 쿼리를 요청한다.
